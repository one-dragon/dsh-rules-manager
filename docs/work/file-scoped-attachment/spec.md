# Spec: 文件级作用域规则的自动附着

Status: ready-for-agent

Slug: `file-scoped-attachment`

## Problem Statement

这个插件把每个规则判成常驻、按需或停用，判定依据只有规则文件里声明的**状态**（frontmatter 的 alwaysApply / enabled / type / trigger / inclusion 等）。但同一个声明在不同厂商那里的含义，往往取决于**另一个字段**是否填了文件匹配式（`globs` / `paths` / `glob` / `pattern` / `fileMatchPattern` / `applyTo`）：

- 有匹配式、没有常驻声明时，Cursor 说这条规则是 “Auto-attached when a matching file is in context”，Claude Code 说它在 Read / Write / Edit 触碰匹配文件时才加载；
- 没有匹配式时，同样的文件在 Claude Code 里是启动即常驻的。

插件目前识别并解析了这六种拼写，也确实据此把规则判成按需；但**按需之后就没有下文了**：匹配式只被保留在规则对象上，既不参与注入，也不参与面板展示。结果是用户明明在规则文件里写了 “这条只对 TypeScript 文件生效”，插件却只能把它一直留在按需索引里，agent 必须猜到要调 `read_rules` 才能看到它——而这恰恰是厂商文档里靠**触碰即附着**免除的那一步。

对用户来说，症状是：一条声明了文件作用域的规则在本会话里从来没有被注入过，即使 agent 刚刚读过、改过完全匹配的文件；面板上也看不出这条规则声明过作用域。

## Solution

插件在本会话内观测**已经结束的、成功的**文件工具调用，记下被触碰的文件路径；当某个按需规则声明的匹配式命中了其中任何一个文件时，这条规则在**后续请求**里按常驻渲染（正文进上下文），在**成本估算**里按常驻计费（不再算作索引行），并在**面板**上标出 “正文常驻”以及原因。

三条边界保证这件事是安全的、可解释的：

1. **只观测，不改写**：附着是「这次会话的视图」，不是规则文件的属性，也永不改写规则的声明状态；关掉开关、退出会话，一切回到文件声明的样子。插件仍然不写任何规则文件。
2. **只认成功结果**：失败的工具调用不算触碰；插件不改写任何工具结果（是 observe，不是 transform）。
3. **有上限、有诊断**：匹配式可能有回溯风险、可能编译不出来、可能超出一次可编译的条数或耗时预算。每一种情况都有明确的诊断码与词典文案，并且**降级方向永远是「保持按需」**，绝不因为匹配开销把请求拖慢。

## User Stories

1. 作为一个 agent，我希望刚刚读过的、声明了文件匹配式的规则在下一个请求里自动以常驻正文出现，以便不必先猜到要调用 `read_rules`。
2. 作为一个 agent，我希望这条附着只发生在我确实触碰了匹配文件之后，以便没有相关文件的项目里上下文不被无关规则占满。
3. 作为一个 agent，我希望附着在一次会话内保持有效（粘性），以便同一批文件上的后续编辑不必反复重新触发。
4. 作为一个 agent，我希望附着对「读」和「写」都成立，以便我改完文件后紧接着需要的规则不会被丢掉。
5. 作为一个 agent，我希望失败的工具调用不触发附着，以便我不会因为一次报错的读取而拿到无关正文。
6. 作为一个 agent，我希望附着后的规则不再同时出现在按需索引里，以便同一条规则不被计两次、也不会误导我再去请求一次。
7. 作为一个 agent，我希望多个 agent 会话之间互不影响，以便并行会话各自只看到自己触碰过的规则。
8. 作为一个使用 Cursor 的用户，我希望规则文件里的 `globs`（逗号分隔的标量）能真正起作用，以便我的自动附着规则不再形同摆设。
9. 作为一个使用 Claude Code 的用户，我希望 `paths`（YAML 列表或逗号串）能真正起作用，以便触碰文件时规则按官方语义加载。
10. 作为一个使用 Qoder 的用户，我希望单数的 `glob` 与官方等价别名 `paths` 都被认，以便官方写法与别名写法都能工作。
11. 作为一个使用 GitHub Copilot 的用户，我希望 `applyTo` 被当作文件作用域，以便 `.instructions.md` 里的唯一必填字段不再被忽略。
12. 作为一个使用 Kiro 的用户，我希望 `fileMatchPattern` 被认，以便 `inclusion: fileMatch` 的组合成立。
13. 作为一个使用 JetBrains AI Assistant 的用户，我希望单数 `pattern` 被认，以便官方示例产物里的写法成立。
14. 作为一个使用 Cline 或 CodeBuddy 的用户，我希望块状 YAML 列表形态的 `paths` 被认，以便多行数组写法与逗号串写法都工作。
15. 作为一个用户，我希望项目级规则的匹配式相对**项目根**求值，以便 `src/**/*.ts` 这样的写法在仓库任意子目录下都成立。
16. 作为一个用户，我希望用户级规则的匹配式相对**该规则自己所在的目录**求值，以便用户目录里的规则不会被项目根污染。
17. 作为一个用户，我希望传给工具的**相对路径**按本次扫描用的同一个工作目录解析，以便相对路径不会因为进程工作目录不同而失配。
18. 作为一个用户，我希望通配符的语义与厂商一致（`*` 不跨目录、`**` 跨目录、`?` 单字符、字符类、花括号展开、`**` 在未指定时包含点文件），以便规则文件的写法不用为插件改写。
19. 作为一个用户，我希望声明了 `manual` 的规则永远不被附着，以便我刻意手动触发的规则不会被自动注入。
20. 作为一个用户，我希望**停用**的规则即使匹配也不被附着，以便我的开关始终说了算。
21. 作为一个用户，我希望来自**被关闭来源**的规则不被附着，以便面板上的来源开关语义保持一致。
22. 作为一个用户，我希望没有声明匹配式的规则保持原有行为，以便这次改动不影响绝大多数规则文件。
23. 作为一个用户，我希望附着后仍然能看到这条规则在文件里声明的状态（仍然显示为 “按需加载”），并在旁边看到 “正文常驻”与原因，以便我知道哪个是文件事实、哪个是本次会话的效果。
24. 作为一个用户，我希望被附着的规则在成本栏位按常驻计费、且不再计入按需索引行成本，以便 token 面板不重复计费。
25. 作为一个用户，我希望被停用（或来源被关）的附着规则按 0 计费并显示停用原因，以便开关的经济学与状态一致。
26. 作为一个用户，我希望回溯风险过高的匹配式被跳过并给出诊断，而不是把一个请求拖慢几秒，以便面板始终可用。
27. 作为一个用户，我希望一次可编译的匹配式条数有上限、超出的规则保持按需并给出诊断，以便超大仓库下的开销可预测。
28. 作为一个用户，我希望匹配式超出耗时预算时降级为按需并给出诊断，以便我仍能在面板上看到原因。
29. 作为一个用户，我希望本会话触碰过的路径数量有上限且按先入先出淘汰，以便内存不随会话时长无界增长。
30. 作为一个用户，我希望附着只在 `injectRules` 打开时发生，以便我关掉注入后插件不做任何额外工作。
31. 作为一个贡献者，我希望附着判定是一个不依赖宿主时序的纯模块，以便它可以用真实夹具穷举测试。
32. 作为一个贡献者，我希望厂商文档依据（URL）写在相关代码旁边，以便后续维护者能回溯每个判断的来源。
33. 作为一个用户，我希望会话切换到另一个工作目录时触碰列表重新开始，以便已经离开的工作区里的规则不会继续常驻。

## Implementation Decisions

- **观测接缝 = 已定型的工具结果**。使用宿主提供的只读结果观测事件（emit 语义，监听器抛错被隔离），**不使用**可变换结果的那条 waterfall。官方指引明确：只读观测走前者，需要变换结果或追加上下文时才用后者。
- **成功才计**：结果标记为错误时直接返回，不做触碰记录。
- **触碰提取按工具族**：单文件参数族（读、读图、写、编辑）取 `file_path`；结构化编辑器族取 `path`；补丁族解析补丁文本里的路径行，覆盖新增 / 更新 / 删除 / 移动四种，其中**移动取目标路径**；**删除计为对该路径最强的触碰**。参数畸形（非字符串工具名、非对象参数、字段缺失或空白）一律返回空列表、永不抛错。
- **解析基准**：相对路径按本次扫描使用的同一个工作目录解析（绝对路径原样保留）。该工作目录会随扫描结果一起缓存，附着判定必须使用它，不能读进程工作目录。
- **会话粘性与隔离**：每个 agent 一份去重、保序的触碰列表，先入先出淘汰，容量有上限；附着判定在同一会话内保持粘性。agent 之间的列表互不共享。触碰列表绑定到它被收集时的工作目录：宿主报告的会话目录发生变化时整份列表作废（尚未被任何请求采用过的列表除外，因为它还不属于任何目录），因为相对路径离开那棵树便无从解析；宿主自己的指令层也在同一事件上重载它的链。
- **面板兜底**：面板 HTTP 请求没有 agent 身份，使用最近一次会话的触碰列表作为兜底来源。
- **只对 active 的按需规则生效**：必须是启用、来源开启、类型为按需、且声明了至少一个匹配式的规则。`manual` 永不附着；声明状态本身永不被改写（附着是视图层概念）。
- **匹配基准目录按作用域**：项目级相对项目根（没有项目根时退化为工作目录）；用户级相对该规则自己所在的目录。
- **匹配器 = 已是既有依赖的那个通配库**，不新增依赖。编译期做两件事：回溯风险启发式跳过、条数上限截断；运行期做一次耗时预算自检。三种降级各自产出诊断码：上限（`attach.limit`）、模式风险（`attach.pattern`）、耗时（`attach.slow`），加上原有的扫描类诊断一起投影到面板。（原先还写了「编译失败跳过」，实现时删掉了：picomatch 4.0.7 对畸形模式不抛错，见 `src/globs.ts` 里带 URL 的实测注释，那一段 `catch` 因此不可达。宿主若把 schema 校验放宽，非数组的 `ruleNames` 会在 `.filter` 处抛错，这是已知的取舍。）
- **附着是视图层的三处映射**（同一份集合喂给三处，避免三套判据）：渲染分区把「按需 + 已附着」当常驻处理；成本模型把该规则按常驻计费并把它从按需索引行成本里剔除；面板行多一个布尔视图字段并给出常驻提示文案（文案与诊断都有中英两份词条）。
- **不引入**：文件系统监听、规则文件的写入、对 `regex` / `trigger` 等其它作用域机制的附着、对厂商体积上限的建模。
- **诊断码的三条新词条**必须中英各一份，且沿用现有 `diag.<code>` 的键名约定，这样帮助文本自动可用。

## Testing Decisions

好测试只测**外部行为**：给定工具调用与磁盘上的规则文件，断言最终注入的块、成本数字、面板行与诊断码，不断言内部实现细节（不测私有函数、不测中间数据结构形状）。

被测试的模块按三档：

1. **附着判定**（纯模块）：穷举触碰提取表（每个工具族、每种字段缺失形态、畸形参数不抛错）、去重与先入先出顺序、作用域基准目录、相对路径解析、上限与三条降级诊断、空触碰短路。
2. **视图映射**：渲染分区（正文取代索引行、规则对象不被改写、用户档与项目档分区正确、停用规则渲染为空）、成本模型（常驻计费、索引成本归零、兄弟规则不受影响、停用仍为 0）、面板纯逻辑（状态、提示键、排序）。
3. **端到端（宿主接缝）**：用假宿主上下文把观测事件、注入前钩子与面板路由串起来，断言：只在注入打开时订阅观测、读匹配文件后注入正文、后续请求持续常驻、不匹配不附着、失败调用不附着、每个 agent 独立、补丁族算触碰、无 agent 时不抛错、面板路由报出附着、会话切换到另一个工作目录后旧列表作废（断言旧目录的规则不再常驻）。

prior art：本仓库已有同型的三层测试——纯逻辑 spec、面板纯逻辑 spec、以及走假宿主的端到端 spec；夹具一律用 `mkdtemp` 建真实目录与真实规则文件，不用 mock 掩盖行为。另有一次**故意变异**验证（把源码里的诊断码改名后，新用例必须变红、其余用例保持通过），用来证明断言真的在咬。

## Out of Scope

- 文件系统监听与规则文件的外部变更跟踪（宿主自己的指令层明确不连续监听外部编辑，本插件同款）。
- 基于 `regex`、`trigger`、`inclusion` 等其它机制的作用域附着；本轮只做「路径匹配」。
- 厂商体积上限（例如某些厂商的 6000 / 12000 / 32K 字符上限）的截断与诊断建模。
- 规则文件之外的写入行为、任何形式的自动修改规则文件。
- GitHub / GitLab issue tracker 集成与 npm 发布（由发布阶段的独立工作项处理）。
